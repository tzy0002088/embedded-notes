## 背景

理解了 DMA master 与多 master 世界([[bus-masters]])之后,拿 USB 控制器的内部 DMA
作为具体实例:USB IN 方向(device→host),DMA 引擎把 DDR 里的数据搬进内部发送 FIFO,
协议引擎再发上总线。core 只出现在一头一尾,中间全是这个"平级 master"自己在跑。

## 提问

1. USB 的 DMA 去 DDR 把数据搬运到内部 FIFO,经历了哪些过程?
2. 触发时机、反压点、一致性前提分别在哪里?

## 理解

### 全景流程图(7 个阶段)

```text
┌──────────────── 阶段 0:CPU 准备(一次性配置) ────────────────┐
│ core:MMIO 写 USB 寄存器(slave 端口)                        │
│   · DMA 源地址(指向 DDR 里的 buffer)                        │
│   · 长度、端点号、使能                                      │
│ core:一致性准备——clean D-cache / DSB(buffer 是 CPU 刚写的)  │
└────────────────────────────┬───────────────────────────────┘
                             │ 端点使能
                             ▼
┌──────────────── 阶段 1:触发 ───────────────────────────────┐
│ USB 协议引擎检查:发送 FIFO 有空位?                          │
│   ├─ 有 ──▶ 产生内部 DMA 请求                               │
│   └─ 无 ──▶ 等(设备侧反压)                                 │
└────────────────────────────┬───────────────────────────────┘
                             │ DMA 请求
                             ▼
┌──────────────── 阶段 2:DMA 发起读事务 ─────────────────────┐
│ USB 内部 DMA 状态机(master 端口)                            │
│   AR 通道:ARADDR=DDR 地址,ARLEN=burst 拍数                 │
│   ARVALID/ARREADY 握手完成                                  │
└────────────────────────────┬───────────────────────────────┘
                             │ 读事务(AR 握手)
                             ▼
┌──────────────── 阶段 3:互连路由与仲裁 ─────────────────────┐
│ 地址译码:DDR 地址窗口 → 路由到 DDR 控制器                   │
│ 多 master 仲裁:和 core/其他 DMA 抢 DDR 端口                 │
│   ├─ 赢得仲裁 ──▶ 放行                                      │
│   └─ 输 ──▶ 反压,ARREADY 拉低,USB DMA 等着                 │
└────────────────────────────┬───────────────────────────────┘
                             │ 读事务放行
                             ▼
┌──────────────── 阶段 4:DDR 控制器执行 ─────────────────────┐
│ AXI 读事务 → DDR 协议波形                                   │
│   ACT(行激活)→ tRCD → READ(列)→ CL 等数据 → 刷新穿插       │
│ 数据从 DRAM 阵列读出                                        │
└────────────────────────────┬───────────────────────────────┘
                             │ 数据返回(R 通道,RVALID/RREADY)
                             ▼
┌──────────────── 阶段 5:数据进 FIFO ────────────────────────┐
│ RDATA 逐拍返回(RLAST 标记 burst 结束)                       │
│ USB DMA 把每拍数据写入内部发送 FIFO                         │
│   ├─ 还没搬完 ──▶ 回到阶段 1 继续发下一个 burst(循环)       │
│   └─ FIFO 写满 ──▶ 暂停,等协议引擎消费                      │
└────────────────────────────┬───────────────────────────────┘
                             │ FIFO 有数据
                             ▼
┌──────────────── 阶段 6:USB 协议引擎发送 ───────────────────┐
│ host 发 IN token → 协议引擎从 FIFO 取数据:                  │
│   并行→串行 → 附 CRC → NRZI 编码 → bit stuffing → PHY 驱动  │
│   D+/D- 差分线 → 数据离开芯片                               │
│   (FIFO 腾出空间 → 又触发阶段 1 的 DMA 请求,流水线继续)     │
└────────────────────────────┬───────────────────────────────┘
                             │ 搬够编程长度
                             ▼
┌──────────────── 阶段 7:完成与通知 ────────────────────────┐
│ DMA 置完成标志(XFRC)→ 产生中断                              │
│ core:中断处理 → 释放/回收 buffer,准备下一包                 │
└─────────────────────────────────────────────────────────────┘
```

### 触发机制:IN token 不是触发者

不是"IN token 来了才去搬"——那样来不及。真实机制是流水线式的:**软件一使能端点,
DMA 就按"FIFO 有空位就搬"的方式预填**;host 的 IN token 消费 FIFO(发走一包),
腾出空间,又触发下一轮搬运。FIFO 满时 DMA 停,这是设备侧的反压;
如果 IN token 来了 FIFO 还是空的,设备回 NAK。

### AXI 读事务的握手细节(阶段 2→5)

```text
clk    _/‾\_/‾\_/‾\_/‾\_/‾\_/‾\_/‾\_/‾\_/‾\_/‾\_/‾\_
ARADDR ───<0x9000_1000>─────────────────────────────
ARVALID ‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾
ARREADY ________‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾
               ↑ 读地址握手完成
   ...若干周期后(排队 + DDR 访问延迟)...
RVALID __________________‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾‾
RDATA  ───────────────────<D0><D1><D2><D3>──────
RLAST  __________________|‾‾‾|‾‾‾|‾‾‾‾‾‾‾‾‾
                                  ↑ 最后一拍拉高:这个 burst 结束
```

### 性能:burst + outstanding 打满带宽

DMA 通常用 burst + outstanding:一次要 8/16 拍,并且不等上一笔回来就连发多个 AR
(多个 burst 在途)。DDR 控制器收到多笔请求后自己重排序、利用多个 bank 并行
(流水线行激活),把总线效率榨出来——这是 DMA 能跑出高吞吐而 CPU 单笔访问做不到的原因。

### 两个反压点,位置不同

| 反压位置 | 谁被停 | 原因 |
|---------|--------|------|
| 互连仲裁输了(DDR 被 core 占着) | USB DMA 的 ARREADY 拉低 | 总线层面 |
| 发送 FIFO 满(协议引擎发得慢) | DMA 状态机自己暂停发请求 | 设备层面 |

### 一致性的前提在阶段 0

DDR 里的 buffer 如果是 CPU 刚写的,启动 USB DMA 前必须 clean D-cache + DSB——
否则 DMA 读到旧数据(多 master 一致性问题的具体体现,见 [[bus-masters]])。
Linux 里这步被封装在 `dma_map_single()` 里:建立 DMA 地址映射 + 按方向刷 cache,
驱动不用手动管;MCU 裸机就得自己 `__DSB()` + clean。

### 一句话总结路径

配置(CPU)→ 触发(FIFO 有空位)→ 读事务(AR 握手)→ 路由仲裁(互连)→ 波形访问(DRAM 阵列)
→ 数据返回(R 通道)→ 进 FIFO → 串行上总线(协议引擎)→ 中断(完成)。
core 只出现在阶段 0 和 7,中间全部是 USB DMA 这个平级 master 自己在跑。

## 要点

- 7 阶段路径:配置 → 触发 → AR 握手 → 仲裁 → DDR 波形 → R 通道返回 → FIFO → 发送 → 中断
- IN token 是"消费者"不是"触发器":DMA 预填 FIFO,发走一包腾出空间才触发下一轮
- 反压两处:总线层(仲裁输,ARREADY 拉低)和设备层(FIFO 满,DMA 自停)
- burst + outstanding + DDR 重排序是 DMA 高吞吐的来源
- CPU 写过的 buffer 要先 clean cache 才能交给 DMA(Linux:dma_map_single)
